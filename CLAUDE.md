## Repository-specific persistence and queue rules

- Persistence is local SQLite through `better-sqlite3` in `lib/db.ts`; there is no MongoDB, Redis, BullMQ, or Docker-backed database setup.
- Keep `lib/db.ts` and database access in server routes / server processes only. Do not import it from client components.
- Use typed row helpers, prepared statements, JSON serialization helpers, and additive schema migrations. The shared database file is configured with `DATABASE_PATH` (default `./data/clipcraft.db`), WAL, and `busy_timeout=5000`; restart both web and worker processes if the path changes.
- Queue state lives in the SQLite `jobs` table. Preserve atomic claims, independent transcription/render polling loops, bounded retries with exponential backoff, restart recovery, and deletion cleanup. Run one worker process per DB; concurrency is within its render loop because startup recovery resets all running jobs.
- Keep changes to persistence/queue boundaries; do not change the video pipeline. Run `npm test`, `npm run typecheck`, and `npm run lint` after relevant changes.

## Repository-specific automatic-pipeline and UI rules

- The upload -> transcript -> viral-detection -> render chain is the product's default path. Keep every step a `jobs` row (never an in-process promise) so a reload or restart resumes at the interrupted step; `lib/pipeline.ts` owns the hand-offs and `recoverAutoPipelines()` runs at worker startup.
- Per-video automation (autoDetect, autoRender, AI clip options) is stored in `videos.pipeline_json` at upload time. `lib/pipeline-defaults.ts` is the only place those defaults and their limits are defined, and it must stay dependency-free (no `lib/db`, no `lib/ai`) because the browser imports it too.
- Never derive pipeline progress from a stored "stage" column: `lib/pipeline-status.ts` recomputes it from queue + clip rows so the UI can't lie. Keep `VideoRecord.status` inside the existing enum.
- Client components must not import `lib/db.ts`; pipeline data reaches the UI through `hooks/use-pipeline.ts` and the `/api/videos/[id]/pipeline` route. `lib/pipeline-ui.ts` holds the presentation-only derivations.
- The clip grid is the single review surface: every tile shows its score and the AI analysis, and Edit + re-render affects one clip only (`POST /api/clips`). Do not add a page-level "render everything" dialog back.

## Repository-specific settings rules

- `lib/app-settings.ts` is the only resolver for app-level settings, and the only rule: **a value saved on /settings, otherwise the built-in default**. `.env.local` is NOT a fallback for the five settings sections (`pipeline|render|ai|worker|profanity`) — do not reintroduce an env tier, and do not add a new `process.env` read for anything that has a form field. Everything without a form field (binary/model paths, CRF, uploads, timeouts, `DATABASE_PATH`) keeps reading env exactly where it always did.
- New settings are added as fields inside an existing section, not as a new env variable. `app_settings` holds one JSON row per section and only what the user saved; `resolveSettings()` stays pure (no SQLite, no `process.env`) so precedence is unit-testable in `tests/app-settings.test.ts`, and `lib/pipeline-defaults.ts` remains the definition of clip options and their limits (`sanitizeSettingsSection('pipeline', …)` delegates to `sanitizePipelineOptions` rather than copying numbers).
- Per-video `videos.pipeline_json` still wins over stored pipeline defaults: defaults are snapshotted at upload so a running pipeline is never changed under the worker. The hook replay follows the AI's `hook_timestamp.start → end` interval at its exact length (`worker/hook-timing.ts`); the stored `hookDuration` is only the fallback for clips without a usable interval, plus the on/off switch (0 disables). Never re-clamp the configured fallback to a shorter "safe" value in the resolver — that makes the field a lie.
- Secrets never leave the server in full. The API returns `maskSecret()` placeholders; a masked entry on save means "keep that stored key" (resolved by mask lookup, so the pool can be reordered and unknown masks are dropped). `app/api/settings/verify` is the only route that sends a key upstream, and it reports `unreachable` rather than guessing. `POST /api/settings {action:'import-env'}` is the single sanctioned read of env keys — an explicit copy into the table, never a resolution tier.
- Worker loop counts are read once at process start (`worker/index.ts`); that is a documented restart requirement, so do not "fix" it by mutating `process.env` from a route. `applyStoredRuntimeSettings()` re-runs before every job for per-job values (profanity mode, and the `REMOTION_CONCURRENCY` slot `worker/remotion-renderer.ts` still reads).
- Built-in caption/overlay presets are seeded with `INSERT OR IGNORE`, so code changes never reach an existing row; `resetCaptionPresets()` / `resetOverlayStylePresets()` (exposed as `{action:'reset'}` on both preset routes, and one button on `/caption-presets`) are the re-sync. They must never touch custom rows, and must only promote a default when no row is marked default — `is_default` is not part of their conflict update, because of the single-default unique index.
- `/settings` is client-state-light by design: `hooks/use-settings.ts` owns fetch/save/reset/verify, and cards that hold a local draft rebuild through a `key={revision}` remount rather than a state-setting effect (the repo lints with `react-hooks/set-state-in-effect`, which rejects the effect form).
